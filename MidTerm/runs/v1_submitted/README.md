# SWEET.TV: индивидуальный экзамен LLM4Rec / ФКН

Дедлайн: **1 ноября 2026, 19:00 МСК**. Реальные данные и вычисления; внешние просмотры и тестовые метки не используются.

## Запуск

Python 3.12. Из корня `MidTerm`:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
PYTHONPATH=src python -m unittest discover -s tests -v
PYTHONPATH=src python -m sweettv.prepare
PYTHONPATH=src python -m sweettv.experiment
PYTHONPATH=src python -m sweettv.verify
PYTHONPATH=src python -m sweettv.report
```

Положите пять оригинальных CSV Kaggle в `sweettv-tv-program-recommender/`; при необходимости измените `data_dir` в `configs/experiment.json`. Принять правила и скачать данные нужно своим аккаунтом. Данные не публикуются в Git. Секреты не нужны для локальных расчётов.

Процесс `prepare` читает CSV через DuckDB, проверяет SHA-256, сохраняет аудит и базу. На выполненном запуске использовались 4 потока и лимит памяти DuckDB 3 GB; фактический пик RSS записан в `artifacts/data_audit.json`. Для временных таблиц и базы нужно несколько GB свободного диска. Процесс `experiment` заново обучает все модели, выбирает стратегию по hold-out и переобучает её на полной разрешённой истории. Время в JSON включает построение и ранжирование; измерения разных запусков могут различаться.

В среде Codex использована `.venv` с системными пакетами встроенного Python; точные версии записаны в `artifacts/environment.json` и `requirements.txt`. Для PDF используется ReportLab и системный шрифт с кириллицей (путь можно задать `SWEETTV_FONT_DIR`). Для визуальной проверки PDF: `pdftoppm -scale-to 1400 -png output/pdf/nikolai_evdokimov_midterm_report.pdf tmp/pdfs/report`.

## Протокол

- Обучение: `[2020-03-09, 2020-05-18)`. Hold-out: `[2020-05-18, 2020-07-27)`, примерно 10 недель. Финальное обучение: 20 недель; прогноз: 12 недель `[2020-07-27, 2020-10-19)`.
- Логи сопоставляются по равенству канала и непустому пересечению полуоткрытых интервалов. Длительность берётся из времён, а не из ошибающегося в 117 строках `duraton`.
- Нулевые ID не являются объектами. Точные дубли удаляются. Пересечения фрагментов объединяются отдельно для каждого пользователя и эфира. Просмотром считается покрытие не менее 80% полного эфира; повторный эфир того же ID даёт новое событие.
- Эфиры, пересекающие границу, не дают обучающих/валидационных меток. Оценка и признаки не используют частичные будущие события.
- Общие кандидаты: положительные ID из эфиров, пересекающих прогнозируемое окно. Уже просмотренные ID разрешены. Будущее расписание используется только для ID и интервалов; даже доступные будущие названия и категории не входят в scoring. Названия для иллюстраций получены отдельно после оценки.
- Ground truth: пять уникальных ID с максимальной частотой квалифицированных эфиров в hold-out, tie-break по ID. Это приближение официального построения цели: описание Kaggle сообщает порог 80%, но не раскрывает обработку фрагментов, границ и равных частот.
- Основная MAP@5 усредняет AP@5 по пользователям шаблона с непустым ground truth. Отдельно публикуются среднее по всем 1260 с нулём для пустых и результат по пользователям с пятью целями. Знаменатель AP: `min(5, |R|)`; попадание повторного предсказания не засчитывается. Порядок ground truth не взвешивается; порядок предсказаний учитывается через precision на рангах.
- Популярность: число уникальных обучающих зрителей программы. Общий fallback: та же популярность среди кандидатов, затем ID по возрастанию. Положительный score метода предшествует нулевому; одинаковые score разрешаются той же популярностью и ID. Каждый список содержит ровно пять уникальных ID.

## Модели

CBF: категории, три жанра, название (токены от двух символов), год, режиссёр и актёры. Модальное значение каждого поля определяется по прошлому расписанию; словарь и IDF обучаются только на этих объектах. Вес жанра/режиссёра 2, актёров 1.5, года 0.5, остальных признаков 1. Векторы TF-IDF и пользовательский профиль L2-нормализуются; score — cosine. Никаких LLM-эмбеддингов или внешних моделей.

Association Rules: корзина — все уникальные просмотренные до границы ID пользователя. Для одиночного правила `i -> j`: `n(i,j)/(n(i)+lambda)`, минимум 3 общих пользователя, максимум 100 следствий на antecedent. Диагональ удаляется. Score — сумма правил с весом `sqrt(частоты antecedent)`. Сравнены lambda=5/20, с затуханием истории и без него.

Дополнительный персональный ориентир Repeat: частота квалифицированных эфиров. `28` в имени означает сумму `2^(-age_days/28)` отдельно по каждому эфиру. Гибрид складывает компоненты, каждую из которых делит на максимум score данного пользователя среди общих кандидатов; нулевой вектор остаётся нулевым. Это эвристические рейтинги, не вероятности.

В первоначальной сетке были 12 конфигураций. После ухудшения Repeat при затухании проверены ещё два гибрида с изменением только этой компоненты. Все результаты, включая проигравшие, сохранены. Проверка абсолютного порога 300 s — отдельная диагностика при неизменном 80% ground truth; она не участвует в выборе. Seed=42 используется для bootstrap; сами модели детерминированы. Сетка и проверочный запуск не обращаются к private score.

## Результаты и доказательства

- `artifacts/data_audit.json`: размеры, SHA-256, nulls, даты, дубли и покрытие.
- `artifacts/validation_protocol.json`: включённые пользователи, кандидаты и ограничения.
- `artifacts/experiments.json`: полная таблица сравнений и времени.
- `artifacts/selection.json`: выбранная стратегия и описательные bootstrap-интервалы.
- `artifacts/user_examples.json`: одни и те же два пользователя, история, ground truth, полные названия, категории, Top-5 всех конфигураций.
- `artifacts/validation_predictions.json`: предсказания и AP каждого пользователя.
- `artifacts/final_submission.csv`: **именно итоговый файл**; SHA-256 в `artifacts/submission_checks.json`.
- `artifacts/tests.log`, `integration_checks.json`, `reproduction_checks.json`: реально выполненные проверки. Два запуска с новым обучением дали одинаковые SHA-256 предсказаний и submission.
- `artifacts/kaggle_result.json` и `artifacts/kaggle_private_score.jpg`: создаются после подтверждённой отправки и получения score. Их отсутствие означает, что score не зафиксирован.

Проверки агента не являются личной проверкой студента. Статус личного объяснения, GitHub-публикации, score и экспорта указан в `report/READINESS.md`.
